# Portfolio v2 — Future Considerations Log

Running record of decisions deferred or rejected during the v2 build, and why — so a later pass doesn't silently re-litigate them or lose the alternative that almost won. Append to this file as new deferrals or rejected-but-viable options come up through the remaining phases (tokens, frontend-design, review passes).

## Fixed this session

- **`.grid-plane` decorative background** — the impeccable hook's "codex-grid-background" finding (a hairline-gradient grid tiled by a fixed pixel cell, a generated-UI tell). Removed entirely during `/design-tokens` rather than reworked — see the new deferred item below for what (if anything) replaces it.
- **`--violet` retired as a brand/gradient hue** — was used in Hero's H1 gradient text, `.conic-ring`'s spinning conic-gradient CTA border, `not-found.tsx`'s matching gradient, `ScrollProgress.tsx`'s 3-stop gradient bar, and one of `GradientField.tsx`'s three ambient wash blobs. All five flattened to solid `--accent`: gradient text → `text-accent`, `.conic-ring` (spinning multi-hue border) → new static `.accent-glow` (single-hue box-shadow ring, no animation), scroll-progress bar → solid `bg-accent`, ambient washes → two `--accent`-only blobs (aqua blob also removed — aqua is status-only, not a decorative hue). `--violet` and `--color-violet` deleted from `globals.css` entirely; verified in-browser (computed styles, no remaining references).
- **Spacing scale formalized** — added named `--spacing-section-y`, `--spacing-section-y-lg`, `--spacing-header-gap`, `--spacing-header-gap-lg`, `--spacing-card`, `--spacing-control` tokens to `globals.css`'s `@theme inline` block (Tailwind v4 auto-generates padding/gap/margin utilities from these). Defined now; not yet applied to existing components' hardcoded utility values — that's a `/frontend-design`-phase adoption task, not a tokens-phase one.
- **Typeface swapped to Geist** in `layout.tsx` (see Superseded decisions below).

## Deferred features (in scope for v2, execution pushed to a later slice)

- **MDX / `/writing` content pipeline** — not built now. Per the design brief, the only requirement for this phase is that `src/content/profile.ts`'s routing/type pattern doesn't get coupled so tightly to case studies that adding a parallel `Post` type + `/writing` route later requires rework. Revisit once there's actual writing content to publish.
- **Live Power BI Publish-to-web embed** (flagship case study) — no sanitized/synthetic dataset is ready yet. v2 ships with an embed *slot* in the case-study layout, holding the existing sanitized dashboard screenshot at the same dimensions, so swapping in the live iframe later is a drop-in, not a layout change.
- **Section-divider data-viz motif** — the design brief's §8 "Texture/decoration" direction called for replacing generic gradient orbs with "subtle animated line/area-chart motifs in section dividers so the background *feels* like BI," tied to real content. Removing `.grid-plane` (an ambient, content-unconnected full-page wash) satisfies the anti-slop half of that direction now; the actual purposeful replacement — a motif scoped to specific section dividers, not a global background — is real new component work for `/frontend-design`, not something invented here. `GradientField.tsx` currently ships with just the two accent washes + vignette, no grid, until that's built.

## Superseded decisions

- **Heading typeface: General Sans → Geist.** During `/design-tokens`, discovered General Sans is a Fontshare font, not a Google Font — `next/font/google` (which self-hosts Inter today with zero extra setup) can't pull it, and getting it would mean downloading files from Fontshare's CDN, which needs explicit user sign-off as an external-file download. Asked the user directly; chose to switch to Geist instead, which is confirmed present in `next/font/google`'s bundled list and self-hosts exactly like Inter does now, no extra files, no download permission needed. General Sans is still viable if the user later wants to explicitly authorize the Fontshare download — see the updated alternatives table below.

## Decisions made during the build (scrollytelling pipeline)

- **`flagship` flag vs `featured`.** The IA growth-plan note suggested branching the flagship-only treatment on `project.featured` "not the slug." But the audit reality is that **two** projects are `featured: true` (it-support AND 211-canada-datathon) — `featured` is the Selected Work / Also Published card split, not "the one flagship." So branching on `featured` would wrongly give both projects the scrollytelling rail. Introduced a distinct optional `Project.flagship` boolean (set only on it-support) as the clean semantic flag. The dashboard slot stays keyed on the separate `project.dashboard` field (a project could have a dashboard without being the flagship, or vice versa) — kept independent on purpose. **If a second project ever earns flagship treatment**, just set its `flagship: true`.
- **No per-stage count-up on the scrollytelling rail.** The brief's signature-interaction wording said "each stage's metric counting up," but `PipelineStage` has only `label`/`detail`/`kind` — no per-node measured figure — and only some stages have a defensible number buried in their detail text. Adding a count-up to each would mean inventing numbers for the stages that don't have one, violating the hard no-fabricated-numbers rule (brief §2/§9). Built the scroll-linked *sequential stage reveal* (the actual differentiator) with each stage's real detail line as the payload, no per-stage counter. **Revisit only if** real per-stage metrics are ever added to the `PipelineStage` data model.

## Decisions made during the de-slop gate

- **`--aqua` muted, not removed.** impeccable's `ai-color-palette` rule flags teal/cyan text (chroma ≥ 80, hue 160–200) on dark as a neon AI-tell. The status hue was muted from `#2dd4a7` (chroma 115) to `#5ea48d` (chroma 70) — under the threshold — so it stays a recognizable teal-green status color without reading as neon. Light theme deepened to `#0f7d5e` for AA. User chose "desaturate" over "keep as-is."
- **Accepted detector deviations recorded** in `.impeccable/config.json` (shared, committed): `kicker-above-heading`, `tiny-text`, `undersized-ui-text`, `all-caps-body` (the monospace data-label motif + section eyebrows — the brief's deliberate Swiss/editorial + BI-label aesthetic, user-confirmed keep) and `overused-font=geist`. These are the brief's intentional design language, not defects; recording them keeps future audits signal-rich.
- **Line-length left at 90–112ch on some secondary prose.** The worst offenders (~155ch Experience text) were constrained to ~68ch; the remaining 90–112ch blocks are an acceptable prose width for a soft quality-tier rule. **Revisit** only if a stricter reading width is wanted — add `max-w-[68ch]` to the remaining full-width text blocks.
- **Two standing false positives** (not fixable without contorting real code): `low-contrast` on the "View work" button (1.0:1 is a backdrop-filter pixel-sampling artifact; the text is near-white on `surface-2`) and `nested-cards` (no literal `.card`-in-`.card` exists — a visual-heuristic match). Left as-is intentionally.

## Superseded during the build

- **Chart library: Recharts → dependency-free inline SVG.** The grill-me round chose Recharts as the charting library for "sparklines / embedded-viz motifs." When actually building the bento hero's mini-KPI tile (the only near-term viz need), installing Recharts pulled in 39 packages and ~100KB+ gzipped for what is one small decorative sparkline — directly at odds with the brief's hard ~100-Lighthouse / fast-LCP goal. Surfaced the tradeoff to the user, who chose to hand-draw the sparkline as a ~60-line inline-SVG component (`ui/Sparkline.tsx`, zero dependencies) and drop Recharts. Recharts was uninstalled cleanly (package.json back to the original 4 deps). **Worth revisiting if** a genuinely richer data-viz need appears later (real multi-series charts, an interactive embedded viz that isn't the Power BI iframe) where hand-rolling SVG would be more work than the dependency's cost is worth — at which point Recharts (or visx, the original runner-up) comes back into play. Note: the 3 high-severity npm-audit findings seen during the brief install were pre-existing in Next's own toolchain (`postcss`, `sharp`, both build-time-only, never shipped to the static client bundle), NOT from Recharts — they persist after uninstall; the only offered fix is a breaking next@16 major, deliberately not taken.

## Decided during `/brief-to-tasks`

- **shadcn/ui adoption — skipped.** The design brief recommended installing shadcn/ui (§3 of the build brief) mainly to get the command palette's portal behavior "for free" via its Dialog/Command primitives. That bug is already fixed by hand this session (`createPortal` to `document.body`), so the main justification is moot. `Modal.tsx` has no reported issues either. Adopting shadcn now would mean replacing working, tested code with an external dependency for no functional gain — contradicts "don't add abstraction beyond what the task requires." **Worth revisiting if**: `Modal.tsx` or another hand-rolled primitive turns up a real accessibility gap (focus trap, ARIA) during the `/design-review` or `/impeccable audit` gate that shadcn's primitives would solve for free.
